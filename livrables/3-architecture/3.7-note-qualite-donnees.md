# Note de qualité des données

> 2026-11-20. Compétence BC05 : « extraire, transformer, charger les données, en évaluant leur qualité et leur pertinence, dans le respect du RGPD ».
> Les chiffres viennent d'un script rejouable : [`annexes/qualite/mesure_qualite.py`](annexes/qualite/mesure_qualite.py), sortie dans [`sortie-2026-11-20.txt`](annexes/qualite/sortie-2026-11-20.txt).

## 1. Deux sources, deux problèmes

| Source | Ce qu'elle contient | Son problème principal |
|---|---|---|
| Base existante (3 tables) | 24 utilisateurs, 18 mandats, 10 secteurs | des données **fausses** : statuts périmés, rôles mélangés (audit, [1.2](../1-audit/1.2-registre-anomalies-risques.md)) |
| Annonces des agences (`annonces.csv`) | 2 556 annonces, 36 colonnes, 5 recherches | des données **incomplètes et hétérogènes** : formats mélangés, champs vides |

## 2. Les annonces, mesurées

**Remplissage moyen : 55,4 %** des cellules dans la source brute.

- **Toujours remplis (100 %)** : identifiant, référence, recherche, type, titre, ville, code postal, date, prix.
- **Souvent vides** : surface en m² (10 %), terrasse (11 %), cave (16 %), charges (20 %), année de construction (25 %), photos (25 %), adresse et coordonnées GPS (51 %), DPE (64 %).
- **Dates de publication en 6 formats** : horodatage Unix (414), `AAAA-MM-JJ` (458), `AAAA-MM-JJThh:mm:ss` (439), `JJ/MM/AAAA` (434), `JJ-MM-AAAA` (402), en toutes lettres (409).
- **Prix** : 382 écrits avec « € », les autres en nombre.
- **Surface** : répartie sur deux colonnes (`surface` ou `surface_m2`), jamais les deux.
- **Étage** : texte libre (« RDC » : 135, « dernier étage » : 125).
- **Cohérence** : 0 identifiant ni référence en double ; 0 annonce rattachée à une recherche inconnue.

## 3. Ce que la normalisation corrige

Le script `normalised/normalised.py` produit un fichier aligné sur la table des biens (`estate`) :

- **un seul format** par colonne : dates en `AAAA-MM-JJ`, prix sans symbole (en euros dans `price_eur`), surface dans une seule colonne, booléens en `True` / `False` ;
- **aucune cellule vide** : une valeur inconnue devient `NULL`, explicitement. On n'invente rien.
  - Exception : une case « présence » jamais à `False` dans la source (jardin, cave…) ; vide veut dire « non ».
- 5 colonnes de la table restent `NULL` partout, faute de source : salles de bain, toilettes, piscine, DPE chiffré, surface du terrain.

Résultat : **70,2 %** des cellules portent une valeur (au lieu de 55,4 %), et le rapport de normalisation compte 0 anomalie sur les 2 556 lignes.

## 4. Ce que la base contrôle à l'entrée

La qualité ne dépend pas que du nettoyage : le schéma refuse une donnée fausse.

- **Contraintes `CHECK`** (168 dans le script de création) : format de l'email, du téléphone et du code postal par pays, montants positifs, dates cohérentes, fin du mandat = signature + 6 mois.
- **Unicité** : un email par compte, une vente par bien, une fiche par compte.
- **Clés étrangères et déclencheurs** : un client ne peut pas être enregistré comme chasseur (anomalie R02 de l'audit).
- **Validation à l'entrée de l'API** : une donnée mal formée est refusée (`422`) avant d'atteindre la base.

## 5. RGPD dans la chaîne

- Les annonces portent des **données de contact** (nom, téléphone, email de l'agent ou du particulier) : elles sont isolées dans une table à part, fermée au compte en lecture seule (registre RGPD, [5.1](../5-transverse/5.1-registre-rgpd.md)).
- La base d'analyse (OLAP) est pseudonymisée ; le compte en lecture seule, lui, lit encore les fiches clients et chasseurs en clair : c'est le trou signalé par la note de souveraineté ([5.4](../5-transverse/5.4-note-souverainete-securite-ia.md), § 1).

## 6. Limites

- Les **doublons entre agences** (un même bien publié deux fois) ne sont pas détectés : aucune clé commune dans la source.
- Les **photos** ne sont pas vérifiées : on garde le lien, il peut casser.
- La qualité est mesurée sur un **jeu d'exercice** de 2 556 annonces ; un vrai flux d'agences sera plus varié.
