## 1. Les protections en place

Deux contrôles à chaque appel, qui ne se remplacent pas : **la clé d'API** dit quel programme appelle, **le jeton** dit quelle personne agit.

| Protection | Ce qu'elle empêche | Où | Décision |
| --- | --- | --- | --- |
| Mots de passe hachés avec **Argon2id** (environ 300 ms et 512 Mo par hachage) | Lire les mots de passe si la base est volée | `utils/security.py` | ADR-016 (choix d'Argon2) |
| **Clé d'API** (en-tête `X-API-Key`) | Un programme inconnu qui appelle l'API | `utils/api_keys.py` | ADR-028 |
| **Jeton JWT** signé, valable **60 min** (JWT : jeton signé qui porte l'identité) | Agir sans s'être connecté | `utils/security.py` | ADR-052 (connexion par jeton) |
| Compte et rôle **relus en base à chaque appel** | Garder ses droits après une désactivation | `utils/current_user.py` | ADR-052 |
| **Droits par rôle**, et « le sien seulement » | Un client qui lit la fiche d'un autre | `utils/roles.py` | ADR-027 (matrice des droits) |
| **Même message** pour un email inconnu ou un mot de passe faux | Deviner quels emails ont un compte | `routes/auth_router.py` | ADR-052 |
| **Frein** : 5 échecs par email, 20 par IP, en 15 min | Essayer des mots de passe sans fin (force brute) | `utils/login_throttle.py` | 2026-11-19 |
| **Code d'activation** à usage unique, valable 7 jours | Un compte que seul un admin pouvait activer | `services/activation_service.py` | user story 01 |
| Requêtes SQL **paramétrées** (SQLModel) | L'injection SQL | `repositories/` | — |
| Effacement = **désactiver et anonymiser** | Garder des données personnelles en clair | `services/anonymization_service.py` | ADR-049 (effacement RGPD) |
| **En-têtes de sécurité** sur chaque réponse ; nom du serveur caché | Deviner le type d'un contenu, afficher l'API dans un autre site, garder une réponse en cache | `main.py` | 2026-11-20 |

Argon2 : **~298 ms** pour le hachage seul (mesuré le 2026-09-22, commentaire de `utils/security.py`) ; les **~430 ms** du test d'attaque du 2026-11-09 sont une autre mesure, par essai de connexion, sans doute la requête entière (non vérifié).

## 2. Extraits de code commentés

### 2.1 Le mot de passe ne se compare jamais avec `==`

```python
# utils/security.py
def verify_password(stored: str, plain: str) -> bool:
    try:
        return _hasher.verify(stored, plain)   # comparaison à temps constant (argon2)
    except VerifyMismatchError:
        return False
    except InvalidHashError:
        spend_password_check(plain)            # même durée pour un compte sans mot de passe
        return False
```

- Un `==` répondrait plus vite quand les premiers caractères sont faux : le chronomètre trahirait le mot de passe.
- `spend_password_check` : un email inconnu répond **aussi lentement** qu'un email connu. Le temps de réponse ne dit pas si un compte existe.

### 2.2 Le frein aux essais en série

```python
# routes/auth_router.py, POST /auth/login
for throttle, key in ((login_throttle.by_email, email_key), (login_throttle.by_ip, ip_key)):
    wait = throttle.retry_after(key)
    if wait is not None:
        raise _too_many(wait)                  # 429 + Retry-After, même avec le bon mot de passe
```

- Pendant le blocage, **même le bon mot de passe** est refusé. Sinon, l'attaquant saurait qu'il a trouvé.

## 3. Les tests d'attaque

- Le 2026-11-09, Gabriel a essayé 4 attaques : injection SQL, XSS et CSRF tenaient ; **l'authentification avait une faille** (15 mauvais mots de passe d'affilée, aucun blocage).
- ➡️ **Faille corrigée le 2026-11-19** par le frein (§ 2.2).
- Le 2026-11-20, tout a été **rejoué** par un script qu'on peut relancer : [`securite/attaques.py`](annexes/securite/attaques.py) (sortie brute : [`securite/sortie-2026-11-20.txt`](annexes/securite/sortie-2026-11-20.txt)). Vraies requêtes HTTP (`httpx`) sur l'API locale, rien écrit en base.

| Attaque | Requête envoyée | Réponse | Verdict |
| --- | --- | --- | --- |
| Injection SQL, champ texte | `POST /auth/login`, email `' OR '1'='1' --` | `401` | ✅ comparé comme un texte, pas lu comme du SQL |
| Injection SQL, chemin | `GET /estates/1 OR 1=1` | `422` | ✅ l'id doit être un entier : refusé **avant** la base |
| Injection SQL, requête empilée | `GET /estates/1;DROP TABLE estate` | `422` | ✅ idem ; la table est toujours là |
| XSS (script glissé dans un champ) | `POST /auth/login`, email `<script>alert(1)</script>` | `401`, JSON | ✅ jamais de HTML : rien à exécuter pour un navigateur |
| CSRF (requête forgée depuis un autre site) | `GET /estates/1` avec un cookie, sans en-tête `Authorization` | `401` | ✅ le jeton n'est jamais un cookie, et aucun site tiers n'est autorisé (pas de CORS) |
| Force brute | 15 × `POST /auth/login`, même email, mots de passe faux | `401` ×5, puis `429` ×10, `Retry-After: 300` | ✅ bloqué **au 6e essai**, pour 5 minutes |

**Bilan : 6 essais sur 6 tiennent.**

### 3.1 L'audit automatique (OWASP ZAP, 2026-11-23)

- **Outil** : OWASP ZAP **2.17.0** (image officielle `zaproxy/zap-stable`), scan d'API `zap-api-scan.py` lu depuis `/openapi.json` : **58 adresses** importées, **159** visitées en tout.
- **Où** : une **copie jetable** de la base de dev et une API à part, avec une clé d'API et un secret de jeton tirés au hasard pour l'occasion ; ni la base de dev ni un vrai secret n'ont servi. Connecté en **Admin**, pour passer la porte d'entrée.
- **Ce qu'il a fait** : **112 980 requêtes** (deux passages), d'attaques connues (injections SQL, commandes, gabarits, XSS, en-têtes…).
- **Résultat** : **0 échec, 119 contrôles passés, 2 avertissements** ; **aucune erreur 500**. Les créations attaquées rendent `422` (entrée refusée) ou `403` (rôle refusé) ; le frein aux essais rend `429`.
- **Avertissement 1, corrigé le jour même** : sans droit, `POST /search-requests/{id}/suggestions` rendait `503` (« Elasticsearch ne répond pas ») au lieu de `401` ou `403` : la route regardait Elasticsearch avant le rôle. L'ordre est inversé, un test le garde (`test_suggestions.py::test_the_role_is_checked_before_elasticsearch`). Les autres `503` viennent d'Elasticsearch, éteint pendant l'audit : la réponse voulue.
- **Avertissement 2, assumé** : pas d'en-tête `Cross-Origin-Resource-Policy`. Il protège les ressources lues par un navigateur ; l'API ne sert que du JSON à des programmes munis d'une clé. À ajouter avec les autres en-têtes, s'il le faut.
- Rapport complet : [`securite/zap-rapport-2026-11-23.html`](annexes/securite/zap-rapport-2026-11-23.html) ; sortie brute : [`securite/zap-sortie-2026-11-23.txt`](annexes/securite/zap-sortie-2026-11-23.txt).
- ⚠️ Limites : un seul rôle connecté (Admin) ; le Swagger `/docs` (seule page HTML) et une attaque répartie sur plusieurs adresses IP ne sont pas couverts.

## 5. Ce que le cours aborde, et les limites

Les sommaires des 4 supports du cours, comparés au code.

### 5.1 En place, en plus du § 1

| Thème du cours | Ce que fait l'API |
| --- | --- |
| Contrôler un jeton reçu | Algorithme **figé** au décodage (`HS256`) : jeton « sans signature » ou expiré refusé |
| Clé secrète robuste | `JWT_SECRET` de **32 caractères au moins**, sinon l'API ne démarre pas |
| Politique de mot de passe (NIST 800-63B) | **12 caractères au moins**, sans règle de complexité ni changement forcé. ⚠️ Le seuil de 12 reste « à confirmer en réunion » (commentaire du code) |
| Ne rien exposer | Une erreur 500 rend un **message neutre et un numéro** ; la pile reste dans le journal |
| Broken Access Control (OWASP) | Rôle vérifié **côté serveur** ; la ligne d'un autre rend `404`, pas `403`, pour ne pas dire qu'elle existe |
| En-têtes de sécurité | `X-Content-Type-Options`, `X-Frame-Options`, `Cache-Control: no-store`, `Referrer-Policy`. ⚠️ Pas de `Content-Security-Policy` (elle casserait le Swagger), et une erreur 500 n'a pas ces en-têtes |

### 5.2 Absent : les limites qu'on assume

| Thème du cours | Ce qui manque | Ce qu'il faudrait |
| --- | --- | --- |
| HTTPS | Pas de TLS en local | Un proxy TLS devant l'API en production |
| Frein partagé | Compteurs **en mémoire**, effacés au redémarrage | Suffisant pour un conteneur ; au-delà, Redis |
| Envoi par email | Pas de serveur d'email : le code d'activation est rendu au manager | Un service d'envoi |
| MFA (second facteur) | Aucun | À prévoir pour Manager et Admin avant une production |
| Révocation d'un jeton | Pas de liste noire, ni de jeton de rafraîchissement (choix ADR-052) | **En partie couvert** : un compte désactivé est refusé à l'appel suivant |
| Mots de passe fuités | Aucune comparaison avec une liste connue | Service à préfixe de hachage ; non fait |
| Chiffrement au repos | Base et sauvegardes MinIO non chiffrées | Chiffrer le disque et le bucket `backup` |
| Rotation des secrets | `JWT_SECRET` et clés d'API fixes | Procédure écrite, sur soupçon de fuite |
| Composants vulnérables | `pip-audit` **dans la CI**, à chaque push : **0 faille** dans nos dépendances ; `pip` épinglé en **26.3** dans le `Dockerfile` le 2026-11-23 (les 6 failles de `pip` 25.0.1 sont parties) | Garder la CI verte |
| Limiter les ressources (OWASP API n° 4) | ✅ **Fait le 2026-11-23** : les listes sont paginées, 100 lignes par défaut, **1 000 au plus** (avant : `GET /estates` rendait 3 219 biens en 1,25 s) | Rien de plus pour les listes |
| Réponse à incident | On **détecte** (journaux dans Elasticsearch), sans marche à suivre pour **répondre** | À écrire avec le plan de reprise |

### 5.3 Non concernés

| Thème | Pourquoi |
| --- | --- |
| SSRF (le serveur appelle une URL donnée) | L'API ne va chercher **aucune** URL d'utilisateur |
| XXE (XML piégé) | Pas de XML, seulement du JSON |
| Désérialisation dangereuse | Aucun `pickle` ; le JSON est validé par des schémas |
| Prototype pollution | Propre au JavaScript ; l'API est en Python |
| Sessions et cookies | **Pas de session ni de cookie** ; jeton dans l'en-tête `Authorization` |
