# Pipeline d'intégration continue et indicateurs de qualité

> BC03 : « concevoir et réaliser un suivi de la qualité de l'application via un cycle automatisé » — preuve attendue : « pipeline CI (ou description) + indicateurs qualité ».
> Le pipeline vit dans le dépôt de l'API : [`Fil-Rouge-API/.github/workflows/ci.yml`](https://github.com/GaSeBeLa/Fil-Rouge-API/blob/main/.github/workflows/ci.yml) (GitHub Actions), depuis le 2026-11-20.

## 1. Ce que fait le pipeline

À **chaque push** et **chaque pull request** vers `main`, GitHub lance deux jobs, sur une machine neuve :

| Job | Étapes | Il échoue si… |
|---|---|---|
| **Tests** | 1. démarre PostgreSQL 16.15 (la même image que `docker-compose`) · 2. crée le schéma (22 tables) et la base de test · 3. lance toute la suite de l'API, avec la couverture · 4. lance les tests d'Airflow | un seul test échoue, ou le schéma ne se crée pas |
| **Audit** | analyse `API/requirements.txt` avec `pip-audit` | une dépendance a une faille connue |

- La base est **jetable** : recréée à chaque passage, puis détruite. Les mots de passe du pipeline sont publics et ne servent qu'à elle : aucun secret du projet n'y figure.
- Le rapport de couverture est gardé comme pièce jointe du passage (`coverage.xml`).

## 2. Les indicateurs

Mesurés le 2026-11-20, en rejouant le pipeline dans des conteneurs neufs (`python:3.12-slim`, `postgres:16.15`) :

| Indicateur | Valeur | Ce qu'il dit |
|---|---|---|
| Tests de l'API | **1 120 réussis**, 7 échecs attendus (`xfail`), **0 échec** | unitaires, intégration sur une vraie base, parcours de bout en bout ([4.4](4.4-rapport-tests.md), [4.3](4.3-tests-fonctionnels.md)) |
| Tests d'Airflow | **126 réussis** | nettoyage des annonces, OLAP, sauvegarde |
| Couverture du code de l'API | **93 %**, lignes et branches (3 553 instructions dont 194 jamais exécutées ; 566 branches) | la part du code qu'au moins un test fait tourner |
| Failles connues des dépendances | **0** (`pip-audit`) | composants vulnérables (OWASP) |
| Durée | ≈ 2 min 20 pour la suite de l'API (141 s) | assez court pour chaque push |

Les 7 `xfail` sont des écarts connus, écrits comme tests : ils passeront au vert le jour où la règle sera codée.

## 3. Comment il a été vérifié

- Avant le premier push, les étapes du fichier ont été **rejouées en local** sur une base neuve. Trois oublis ont été trouvés et corrigés : un secret de test trop court, des clés d'API absentes, une base de développement vide.
- Le premier passage sur GitHub reste à constater après le push : son résultat s'affiche dans l'onglet « Actions » du dépôt.

## 4. Limites

- **Pas d'analyse statique** (types, style) dans le pipeline : `pyright` se lance à la main.
- Trois tests dits « unitaires » (journal d'accès) passent par la vraie base : ils exigent qu'elle soit remplie. À isoler.
- Pas de seuil de couverture bloquant : 93 % est mesuré, pas imposé.
- Pas de déploiement : le projet n'est pas hébergé (périmètre du sujet).
